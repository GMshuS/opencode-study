# 测试验证 Skill

## 核心原则

- **纯执行器** — 不判断"项目该不该有测试""该用什么框架"，只负责执行
- **优先项目脚本** — 有 `scripts.test` / Makefile `check` / ctest 等就用项目的，不自行拼命令
- **只报告不修复** — 不改业务代码、不改测试、不安装依赖
- **只报事实，不判阻塞** — 只输出执行结果与结论，是否阻断、如何处置由调用流程自行判定
- **跑不起来 ≠ 失败** — 命令无法启动 → `⏭️ 阻断 — 原因`，不记通过也不判失败
- **防挂死** — 默认超时 300s（指定 `scope` 时 120s）；超时记 `❌ 超时`，禁止静默当通过
- **防隐式下载** — 用 `npx --no-install vitest --version`，而非 `npx vitest --version`

## 输入参数（均可选）

| 参数 | 说明 |
|---|---|
| `command` | 运行命令；未指定时按项目已有配置推断 |
| `scope` | 限定范围：文件路径 / 包路径 / 用例名过滤 |
| `baseline` | 上一轮用例级结果，用于「由绿转红」检测 |
| `timeout` | 覆盖默认超时（秒） |

## 工作流程

### 步骤 1：命令解析（不做框架选型）

1. 传入 `command` → 直接使用，进入步骤 2
2. 未传入 → 按项目已有配置推断（「优先项目脚本」原则）：`package.json` 的 `scripts.test`、`Makefile` 的 `check`、`CMakeLists.txt` 的 ctest 等

### 步骤 2：执行测试

按 `scope` 限定范围执行。

### 步骤 3：结果分类

| 执行结果 | 结论 | 性质 |
|---|---|---|
| 命令执行成功，用例全绿 | `✅ 通过` | — |
| 命令执行成功，有用例断言失败 | `❌ N 项失败` | **代码问题** |
| 命令不存在 / 依赖缺失 / 构建产物缺失 | `⏭️ 阻断 — 原因` | **环境问题**，须附原始错误输出 |
| 超过 `timeout` | `❌ 超时` | — |

> **区分要点**：「跑起来结果不对」是代码问题，「跑不起来 / 装不上」是环境问题。
> 存疑时按代码问题处理，且必须附实际命令的原始错误输出——禁止凭猜测判定环境问题。

### 步骤 4：报告

```
═══ 测试验证报告 ═══
  命令: {...}
  范围: {全量 | scope...}
  结果: {a} 通过 / {b} 失败 / {c} 跳过 / {❌ 超时 | ⏭️ 阻断}
  用例级结果:
    ✅ {用例名}
    ❌ {用例名} — {文件:行} — {断言消息 / 原始输出}
  与基线对比（仅传入 baseline 时）:
    🔴 由绿转红: {用例名}（上轮 ✅ → 本轮 ❌）

═══ 结论: {✅ 通过 | ❌ N 项失败 | ❌ 超时 | ⏭️ 阻断 — 原因} ═══
```
